## 마일스톤 (우선순위별)

### 1차 마일스톤: Priority 1 (핵심 기능)

**목표**: ContentLoader → 프롬프트 주입 시스템 구현

**작업 항목**:
1. `prompt_builder.py`에 ContentLoader 통합
2. 일간, 격국, 용신, 희신 콘텐츠 주입 로직 구현
3. 콘텐츠 없을 시 graceful handling
4. 단위 테스트 작성
5. 통합 테스트 수행

**성공 기준**:
- ContentLoader 콘텐츠가 프롬프트에 정확히 주입됨
- 콘텐츠가 없어도 프롬프트 생성이 중단되지 않음
- 기존 기능에 대한 회귀 없음

### 2차 마일스톤: Priority 2 (핵심 판단 요약)

**목표**: 핵심 판단 요약 블록 추가

**작업 항목**:
1. 일간 강약 분석 함수 구현
2. 월령 특성 추출 함수 구현
3. 오행 균형 분석 함수 구현
4. 핵심 십신 식별 함수 구현
5. 요약 블록 생성 및 프롬프트에 추가
6. 단위 테스트 작성

**성공 기준**:
- 신강약, 월령, 오행, 핵심 십신이 정확히 식별됨
- 요약이 프롬프트에 명확한 섹션으로 추가됨
- LLM 해석 품질 향상이 관찰됨

### 3차 마일스톤: Priority 3 (질문 우선순위)

**목표**: 질문 우선순위 시스템 구현

**작업 항목**:
1. 질문 키워드 분석 함수 구현
2. 질문 카테고리 분류 시스템 구현
3. 카테고리별 가중치 조정 로직 구현
4. 출력 형식 표준화
5. 단위 테스트 작성

**성공 기준**:
- 질문이 있을 때 관련 항목이 상세히 설명됨
- 질문이 없을 때 균형 잡힌 해석이 제공됨
- 카테고리 분류 정확도 80% 이상

### 4차 마일스톤: Priority 1 (Streamlit 통합 검증)

**목표**: Streamlit UI에서 개선된 프롬프트 시스템 검증

**작업 항목**:
1. Streamlit UI 테스트 (기존 코드 그대로 사용)
2. API 엔드포인트 테스트
3. 엔드투엔드 테스트
4. 사용자 경험 테스트
5. 성능 모니터링

**성공 기준**:
- Streamlit UI에서 개선된 해석이 정상 표시됨
- 에러 처리가 적절히 작동함
- 응답 시간이 허용 범위 내 (< 10초)

## 기술 접근 방식

### 아키텍처 설계

**기존 아키텍처**:
```
Streamlit UI → API → InterpretationService → prompt_builder.py → LLM
                                    ↓
                              (ContentLoader 미사용)
```

**개선된 아키텍처**:
```
Streamlit UI → API → InterpretationService → prompt_builder.py → LLM
                                    ↓
                              ContentLoader (신규 통합)
                                    ↓
                              (일간/격국/용신/희신 콘텐츠)
```

### 핵심 설계 결정

**결정 1: ContentLoader 통합 위치**
- **선택**: `prompt_builder.py`에 직접 통합
- **이유**:
  - 프롬프트 생성 로직의 일관성 유지
  - ContentLoader 조회 실패 시 graceful handling 용이
  - 단위 테스트 작성 용이

**대안**:
- `InterpretationService`에서 통합: 서비스 계층이 비대해짐
- 별도 `ContentInjector` 클래스 생성: 과도한 추상화

**결정 2: 핵심 판단 요약 생성 방식**
- **선택**: `prompt_builder.py`에서 계산 결과 기반으로 즉시 생성
- **이유**:
  - 간단한 분석 로직이므로 별도 모듈 불필요
  - 프롬프트 생성과 밀접하게 연관됨
  - 재사용성이 낮음 (프롬프트 전용)

**대안**:
- 별도 `AnalysisSummarizer` 클래스: 과도한 추상화
- `SajuService`에서 계산: 이미 책임이 많음

**결정 3: 질문 우선순위 처리 방식**
- **선택**: 키워드 기반 간단 분류
- **이유**:
  - MVP 단계에서 복잡한 NLM 불필요
  - 사주 도메인 특화 키워드로 충분히 정확
  - 추후 LLM 기반 분류로 확장 가능

**대안**:
- LLM 기반 분류: 비용과 지연 시간 증가
- 규칙 기반 복잡 분류: 유지보수 부담

### 구현 전략

**단계 1: ANALYZE (기존 동작 이해)**
- `prompt_builder.py`의 현재 구조 분석
- ContentLoader API와 데이터 구조 이해
- 기존 프롬프트 형식과 토큰 사용량 측정

**단계 2: PRESERVE (기존 동작 보존)**
- 기존 프롬프트 구조 유지
- 하위 호환성 보장 (ContentLoader 없이도 동작)
- 기존 테스트 케이스 통합

**단계 3: IMPROVE (개선 구현)**
- ContentLoader 주입 로직 추가
- 핵심 판단 요약 생성
- 질문 우선순위 처리

## 위험 및 대응 계획

### 위험 1: 토큰 사용량 급증

**확률**: 중간 (60%)
**영향**: 높음 (API 비용 증가, 응답 시간 지연)

**대응 계획**:
1. 콘텐츠 길이 제한 (핵심 부분만 추출)
2. 콘텐츠 요약 전략 (첫 문단, 핵심 태그)
3. 토큰 모니터링 및 경고 시스템

### 위험 2: ContentLoader 로딩 실패

**확률**: 낮음 (20%)
**영향**: 중간 (기능 일부 작동 안 함)

**대응 계획**:
1. Graceful degradation: 콘텐츠 없이도 프롬프트 생성
2. 로깅 및 모니터링 강화
3. 콘텐츠 파일 검증 도구

### 위험 3: LLM 해석 품질 저하

**확률**: 낮음 (15%)
**영향**: 높음 (사용자 만족도 저하)

**대응 계획**:
1. A/B 테스트로 품질 비교
2. 프롬프트 튜닝 및 최적화
3. 롤백 계획 (기존 프롬프트로 복원)

**대상**:
- `build_interpretation_prompt()` 함수
- `_build_core_summary()` 함수 (신규)
- `_extract_question_category()` 함수 (신규)

**대상**:
- InterpretationService → prompt_builder.py → ContentLoader 통합

**시나리오**:
1. 기본 사주 해석 (질문 없음)
2. 특정 질문이 있는 해석 (직업, 연애, 재물)
3. ContentLoader 콘텐츠가 없는 경우
4. 에러 처리 (API 실패 등)
